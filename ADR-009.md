# ADR-009: User-Configured Fiscal Sources, Universal Accounting Adapters, and AI-Assisted Rule Extraction

* **Status:** Proposed / Architectural Blueprint
* **Date:** 2026-11-13
* **Context:** Internationalization & Jurisdiction-Agnostic Scaling
* **Related ADRs:** ADR-001 (Local-only financial data), ADR-006 (Regulatory Monitor trust boundary), ADR-007 (Signed regulatory package ingestion), ADR-008 (Local integration SDK)

## Context and Problem Statement

FinRadar's deterministic core and local-first architecture are inherently jurisdiction-agnostic. However, hardcoding accounting connectors (e.g., 1C) or maintaining manually verified statutory tax packs (e.g., Georgia pilot rules) creates a bottleneck for rapid international expansion across diverse regulatory regimes (EU, UK, US, MENA).

At the same time, allowing the core calculation engine to directly scrape arbitrary user-provided government URLs would violate FinRadar’s core safety invariants:
1. **Determinism & Auditability:** Unstructured HTML/PDF changes on government portals cannot be fed directly into financial calculations without risking silent corruption or non-reproducible forecasts.
2. **Trust Boundary (ADR-006):** The core calculation engine must remain strictly offline and isolated from external network endpoints.

## Decision

We will decouple jurisdiction-specific data ingestion from the deterministic calculation engine by introducing **User-Configured Integration Profiles** in the Regulatory Monitor and Local Integration SDK layers, governed by a strict **Human-in-the-Loop (HITL)** verification gate.

### 1. Universal Accounting & Bank Ingestion (User-Configurable Mapping)
In addition to native read-only adapters (such as the 1C adapter shell in ADR-008), users will be able to configure custom ingestion profiles in application settings without code changes:
* **Standardized Financial Formats:** Native support for ISO 20022 (`CAMT.053`), `MT940`, and `OFX` bank statements.
* **Declarative Column Mapper:** A UI-configured mapping schema allowing users or accountants to map arbitrary CSV/XLSX exports from any local ERP/accounting software (e.g., QuickBooks, Xero, Odoo, DATEV, Sage) into FinRadar's canonical ledger batch format.

### 2. Three-Tier User-Configured Fiscal Sources
Users can specify their local fiscal authority or regulatory feed in the **Regulatory Monitor** settings (operating outside the offline core boundary per ADR-006) via three supported modes:
* **Tier A — Official Machine-Readable Endpoints:** Direct connection to standardized government APIs or open statutory feeds (e.g., PEPPOL, HMRC MTD, central bank rate feeds) using structured XML/JSON schemas.
* **Tier B — AI-Assisted Regulatory Extractor (Human-in-the-Loop):** Users input a local fiscal authority URL or upload statutory tax documents (PDF/HTML). An isolated AI parser extracts tax rates, filing deadlines, and obligation triggers into a draft `RegulatoryRulePack` JSON schema. **Strict Invariant:** Draft packs are never applied automatically; they require explicit review and local cryptographic signing by the user/accountant via a verification UI before crossing the trust boundary into the core engine (ADR-007).
* **Tier C — Third-Party / Partner Signed Feeds:** Accounting firms, tax advisors, or community maintainers can publish versioned, cryptographically signed JSON rule packs via custom feed URLs that enterprises subscribe to in settings.

## Consequences

### Positive
* **Zero-Code Geographic Expansion:** FinRadar can be deployed in any jurisdiction without requiring the core engineering team to manually code local tax laws or ERP integrations.
* **Preservation of Core Invariants:** AI remains strictly confined to text/rule extraction outside the calculation boundary. The core engine continues to execute 100% deterministic math on verified, versioned, and signed inputs.
* **Enterprise & Audit Compliance:** Every custom mapping and AI-extracted rule pack generates an immutable audit log entry showing the source URL, extraction timestamp, and the human approver who signed off on the rule.

### Negative / Trade-offs
* **Onboarding Friction for Non-Technical Users:** Configuring custom CSV mappings or reviewing AI-extracted tax rules requires basic financial literacy (typically a bookkeeper or CFO). This is mitigated by providing pre-built community/partner templates for major markets.
* **Parser Maintenance:** Government websites frequently change layouts or anti-bot protections, meaning Tier B URL fetching may occasionally require manual PDF upload fallbacks by the user.
