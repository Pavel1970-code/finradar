# FinRadar: план перехода к работающему MVP

Дата: 2026-07-19  
Исходное состояние: commit `fec212c` плюс документация текущего состояния  
Цель этапа: работающий Windows desktop MVP на полностью вымышленных данных

## 1. Определение готового MVP

MVP считается готовым, если на чистом компьютере пользователь может:

1. запустить приложение без ручной подготовки базы данных;
2. увидеть один основной экран без технических терминов про коннекторы и внутренние модули;
3. нажать кнопку «Дать прогноз»;
4. получить прогноз на 30 дней с датой первого кассового разрыва, минимальным остатком и требуемым финансированием;
5. увидеть, каких данных не хватает и как это ограничивает точность прогноза;
6. увидеть рассчитанное вымышленное налоговое обязательство, возможную пеню/штраф и отдельный stress-сценарий;
7. открыть сравнение «было — стало — влияние на прогноз» для вымышленного изменения ставки;
8. повторить расчёт и получить тот же результат при тех же исходных данных;
9. перезапустить приложение и увидеть историю выполненных прогнозов;
10. выполнить весь сценарий при отключённом интернете.

MVP должен поставляться как проверенная Windows-сборка. Для внутреннего MVP допустим неподписанный ZIP/portable artifact. Установка на компьютеры внешних пользователей потребует отдельного подписанного installer.

## 2. Что входит в MVP

- Core desktop application.
- Локальная SQLite-база и автоматические миграции.
- Набор встроенных вымышленных сценариев компании.
- Fixture accounting connector, имитирующий полный снимок 1С.
- Fixture bank connector, имитирующий банковские операции.
- Детерминированный cash forecast.
- Вымышленные процентные налоговые правила, пени и штрафы.
- Основной и stress forecast.
- Data-readiness report и конкретные сообщения о недостающих данных.
- Сравнение двух версий вымышленного налогового правила.
- Локальная история синхронизаций и анализов.
- Отдельная демонстрация безопасного импорта подписанного вымышленного regulatory package без интернета.
- Windows portable build и acceptance checklist.

## 3. Что не входит в этот MVP

- Реальная 1С, COM, OData, HTTP или файловый обмен с конкретной конфигурацией.
- Реальный банковский API, OAuth и банковские credentials.
- Загрузка документов с сайтов Грузии.
- Реальные налоги, ставки, сроки, льготы, возвраты, штрафы и пени Грузии.
- AI, RAG, OCR, embeddings и vector database.
- Автоматическая юридическая активация новых правил.
- Облачные сервисы, телеметрия и отправка финансовых данных наружу.
- Multi-user deployment.
- Работа с реальными финансовыми данными до реализации encryption at rest и backup/restore.

Причина ограничения: фиктивный AI или фиктивный HTTP-коннектор не подтверждают работоспособность реальной интеграции. Для MVP полезнее полностью завершить пользовательский и расчётный контур на контролируемых данных.

## 4. Целевой пользовательский сценарий

```text
Запуск приложения
        │
        ▼
Главный экран: компания, дата данных, состояние готовности
        │
        ▼
Кнопка «Дать прогноз»
        │
        ├─> чтение вымышленного accounting snapshot
        ├─> чтение вымышленного bank batch
        ├─> проверка и reconciliation
        ├─> выбор active fictional rules
        ├─> deterministic analysis
        └─> сохранение audit history
        │
        ▼
Результат
  ├─ прогноз денежных средств
  ├─ кассовый разрыв и требуемая сумма
  ├─ недостающие/устаревшие данные
  ├─ налоги, пени, штрафы
  ├─ основной и stress-сценарий
  └─ «было — стало — влияние»
```

Пользователь не должен выбирать тип коннектора, формат снимка, rule ID или synchronization cursor.

## 5. Рабочие этапы

### Этап 0. Зафиксировать MVP-контракт

Цель: исключить изменение объёма работ во время реализации вертикального сценария.

Работы:

1. Утвердить три обязательных демонстрационных сценария.
2. Зафиксировать ожидаемые числовые результаты каждого сценария.
3. Зафиксировать 30-дневный горизонт MVP.
4. Зафиксировать русский язык интерфейса.
5. Утвердить, что все названия компаний, документов, правил и операций явно помечены как вымышленные.

Обязательные сценарии:

| Сценарий | Входные особенности | Ожидаемое поведение |
| --- | --- | --- |
| `base_cash_gap` | Полные данные, известные поступления, расходы и вымышленный налог | Прогноз доступен; показывается конкретный кассовый разрыв |
| `missing_recent_data` | Устаревшая банковская выписка и банковская операция без бухгалтерского соответствия | Прогноз `limited`; перечисляются недостающие последние дни и неучтённая операция |
| `fiscal_change_and_delay` | Новая вымышленная ставка, частично неоплаченный налог и просрочка | Показываются «было — стало», пеня и ухудшение stress forecast |

Результат этапа:

- golden JSON для трёх сценариев;
- таблица ожидаемых сумм, дат и readiness status;
- запрет случайного использования реальных идентификаторов и ставок.

Критерий завершения:

- один и тот же сценарий имеет заранее утверждённый результат до начала UI-работ.

### Этап 1. Собрать application facade и состояния запуска

Цель: убрать расчёт из `main.py` и сделать один управляемый пользовательский use case.

Работы:

1. Создать `ForecastApplicationFacade` поверх существующего `synchronize_and_forecast`.
2. Ввести состояния `idle`, `running`, `result`, `error`.
3. Передавать в facade accounting connector, bank connector, rule provider и recorders через зависимости.
4. Создавать `QApplication` и окно до запуска анализа.
5. Запускать анализ по нажатию кнопки, а не до открытия окна.
6. Выполнять анализ в Qt worker, чтобы будущая реальная синхронизация не блокировала UI.
7. Преобразовать исключения подключения, миграции и повреждения истории в пользовательские ошибки.
8. Не передавать доменные dataclass напрямую во все UI-компоненты; создать presentation/view models.

Результат этапа:

- окно открывается в состоянии `idle`;
- кнопка запускает существующий аналитический pipeline;
- повторное нажатие выполняет новый run;
- исключение не закрывает приложение.

Тесты:

- facade success/blocked/error;
- защита от двух одновременных запусков;
- повторный запуск после ошибки;
- UI state transitions.

Критерий завершения:

- полный base-сценарий запускается одной кнопкой без ручных действий с БД.

### Этап 2. Встроить воспроизводимые вымышленные источники

5. Реализовать `ScenarioBankConnector` через существующий bank protocol.
6. Не использовать основные таблицы `companies/cash_accounts/cash_flow_items` как источник demo-сценария.
7. Сохранять полученный canonical snapshot только в существующую audit history.
8. Автоматически выбирать `base_cash_gap` при первом запуске.

10. Добавить fixture provenance: scenario ID, version, captured_at и source references.

Результат этапа:

Тесты:

Критерий завершения:

### Этап 3. Подготовить вымышленные правила и расчётные golden cases

Цель: задействовать уже реализованные fiscal modules в реальном startup flow MVP.

Работы:

4. Создать вымышленное правило штрафа, требующего решения органа.
5. Создать `DemoFiscalRuleBootstrapper`.
6. Идемпотентно провести правила через `candidate -> validated -> reviewed -> active` с audit reasons.
7. Не добавлять специальные demo-ветвления в доменные формулы.
8. Зафиксировать obligation keys и source references.
9. Добавить сценарий частичной оплаты и уже начисленной бухгалтерией пени.

Результат этапа:

- current startup загружает не пустой active rule set;
- налоги, пеня и штрафы реально проходят существующий deterministic pipeline;
- повторный bootstrap не создаёт новые версии.

Тесты:

Критерий завершения:

### Этап 4. Реализовать основной пользовательский интерфейс MVP

Цель: дать результат без необходимости понимать внутреннюю архитектуру.

Экран должен содержать:

1. название вымышленной компании и дату актуальности данных;
2. одну основную кнопку «Дать прогноз» / «Обновить прогноз»;
3. readiness banner: данные полные, есть ограничения или анализ заблокирован;
4. четыре основные метрики: текущий остаток, остаток на конец горизонта, минимальный остаток, дата первого разрыва;
5. требуемое финансирование;
6. график ежедневного остатка на 30 дней;
7. краткий список ближайших значимых выплат;
8. отдельный блок «Каких данных не хватает»;
9. отдельный блок «Налоги и возможные последствия»;
10. переключатель «Основной прогноз / стресс-сценарий»;
11. время последнего успешного расчёта;
12. понятное сообщение при ошибке и кнопку повтора.

UI не должен показывать по умолчанию:

- rule IDs;
- JSON schema versions;
- synchronization cursors;
- content hashes;
- названия внутренних Python modules;
- private/public key details.

Для тестирования MVP допустим выбор демонстрационного сценария в разделе «Демо-режим». Этот выбор не должен выглядеть как настройка реального подключения.

Результат этапа:

- пользователь выполняет полный сценарий только из окна;
- все существенные доменные результаты имеют русское представление;
- длинные issues не разрушают layout.

Тесты:

- Qt smoke tests для трёх сценариев;
- idle/running/result/error states;
- blocked forecast;
- stress toggle;
- длинные тексты и resize 960×640 / 1200×760;
- отсутствие технических идентификаторов в основном представлении.

Критерий завершения:

- независимый тестировщик понимает результат без объяснения архитектуры разработчиком.

### Этап 5. Реализовать «было — стало — влияние на прогноз»

Цель: показать влияние изменения правила, не смешивая AI и расчёты.

Работы:

1. Создать `FiscalComparisonService`.
2. На одном accounting snapshot выполнить анализ с baseline rule set и current rule set.
3. Сравнивать:
   - ставку;
   - размер обязательства;
   - дату платежа;
   - минимальный остаток;
   - дату первого кассового разрыва;
   - требуемое финансирование.
4. Хранить обе ссылки на rule ID/version и analysis run.
5. Не считать разницу AI-моделью.
6. В UI показывать только понятные значения и ссылку «Подробности расчёта».
7. Явно разделить фактическое изменение правила и stress assumption.

Результат этапа:

- экран показывает «раньше 5%, теперь 7%» и числовое влияние на прогноз;
- одинаковые rule sets дают нулевую delta;
- неполные данные дают `unresolved`, а не выдуманное сравнение.

Тесты:

- deterministic deltas;
- изменение суммы без изменения даты;
- изменение даты;
- отсутствие требуемой metric;
- no-double-counting в обоих прогнозах.

Критерий завершения:

- сравнение полностью воспроизводимо из сохранённых snapshot и rule versions.

### Этап 6. Завершить предварительный отчёт о данных

Цель: сделать отсутствие данных отдельным результатом, а не технической ошибкой.

Работы:

1. Ввести presentation mapping для каждого текущего issue code.
2. Для каждого issue показывать:
   - чего не хватает;
   - за какой период;
   - какое влияние это оказывает;
   - блокирует ли это прогноз.
3. Добавить агрегирование повторяющихся mapping errors.
4. Отдельно показывать:
   - устаревший остаток;
   - отсутствующий платёжный календарь;
   - отсутствующие accounting metrics;
   - неполное банковское покрытие;
   - банковские операции без бухгалтерской записи;
   - неоднозначное сопоставление;
   - несовместимую валюту;
   - отсутствующую ставку пени.
5. Не утверждать, что бухгалтер забыла внести расход, если независимого банковского факта нет.

Результат этапа:

- `missing_recent_data` выдаёт конкретный предварительный отчёт;
- при `blocked` пользователь видит необходимые действия, а не пустое окно.

Тесты:

- каждый issue code имеет пользовательский текст;
- неизвестный issue имеет безопасный fallback;
- plural forms для количества дней и операций;
- source reference не раскрывается в основном тексте без запроса подробностей.

Критерий завершения:

- любой отказ в расчёте сопровождается конкретной причиной и влиянием.

### Этап 8. Проверить regulatory boundary на вымышленном пакете

Цель: подтвердить существующую one-way архитектуру без включения интернета.

Работы:

1. Создать публичный вымышленный документ fixture.
2. Использовать только structured/manual extraction; AI не имитировать.
3. Сформировать candidate с evidence excerpt и rule data.
4. Подписать package тестовым Monitor key.
5. Импортировать package в Core через существующий importer.
6. Реализовать mapping только поддерживаемого fictional percentage candidate в `FiscalRuleVersion` со статусом `candidate`.
7. Не активировать imported candidate автоматически.
8. Для MVP отдельно использовать заранее reviewed bundled rule set.
9. Добавить внутренний диагностический экран/команду, показывающую accepted/quarantined package, без вывода key material.

Результат этапа:

- полный локальный Monitor → signed package → Core candidate test проходит;
- candidate не влияет на прогноз до review/activation;
- финансовые поля отклоняются.

Тесты:

- invalid signature/quarantine;

Критерий завершения:

### Этап 9. Подготовить Windows portable MVP

Цель: получить фактически запускаемый Windows artifact, а не только spec files.

Работы:

1. Поднять чистую Windows 11 VM x64.
2. Установить Python 3.13 и build dependencies в отдельное окружение.
3. Собрать Core и Monitor через существующие PyInstaller specs.
4. Включить demo JSON resources в Core artifact.
5. Проверить создание БД в `%LOCALAPPDATA%`.
6. Проверить migrations на fresh install и upgrade старой prototype DB.
7. Запустить Core без интернета.
8. Выполнить boundary inspection: Core не содержит Monitor/network modules; Monitor не содержит Core/SQLAlchemy/PySide.
9. Проверить high-DPI, 100%/125%/150%, русские шрифты и минимальное окно.
10. Создать portable ZIP с version manifest и checksum.
11. Не называть этот ZIP production installer.

Дополнительно, если в MVP запускается Monitor:

1. применить ACL/firewall scripts;
2. выполнить S4U и cross-identity acceptance;
3. оставить downloader отключённым;
4. проверить, что Core не может писать в exchange, а Monitor не видит Core data.

Результат этапа:

- versioned Windows ZIP;
- заполненный acceptance report;
- список известных Windows defects.

Критерий завершения:

- сценарии MVP проходят на чистой Windows VM без установленного Python.

## 8. Риски плана

| Риск | Последствие | Мера |
| --- | --- | --- |
| Попытка одновременно подключать реальную 1С | Задержка UI MVP из-за неизвестной схемы источника | Сначала scenario connector через тот же protocol |
| Использование старых prototype tables как универсальной модели | Дублирование snapshot и проблемы incremental sync | Demo resources остаются внешним read-only source |
| Слишком ранний AI/RAG | Невоспроизводимые результаты и размытие ответственности | В MVP только deterministic explanations |
| Автоматическая активация imported rule | Непроверенное правило влияет на деньги | Candidate остаётся неактивным до review |
| Смешивание основного и stress forecast | Пользователь воспринимает возможный штраф как начисленный | Раздельные представления и labels |
| Добавление банковского HTTP в Core | Нарушение локальной границы | Только fixture/local-file adapter в MVP |
| Отсутствие Windows проверки до конца | Накопление platform defects | Ранний smoke build после этапа 4, финальная сборка на этапе 9 |
| Рост БД из-за полных snapshots | Размер не оценён до пилота | Нагрузочный тест 100/1000 runs на этапе 10 |
| Реальные данные попадут в незашифрованную БД | Нарушение конфиденциальности | Явная маркировка demo-only и запрет реального импорта |

## 9. Контрольные точки

### Контрольная точка A — работающая вертикаль

После этапов 0–3:

- данные приходят из фиктивных accounting/bank connectors;
- readiness, forecast, tax, penalty и history формируются одним facade;
- результаты подтверждены golden tests;
- UI ещё может оставаться техническим.

### Контрольная точка B — пользовательский MVP

После этапов 4–7:

- пользователь нажимает одну кнопку;
- видит прогноз, пробелы, fiscal risks, comparison и history;
- не взаимодействует с внутренними модулями.

### Контрольная точка C — архитектурный MVP

После этапа 8:

- подписанный публичный candidate проходит one-way boundary;
- автоматически в расчёт не попадает.

### Контрольная точка D — передаваемый MVP

После этапов 9–10:

- portable Windows build проверен на чистой VM;
- acceptance report и известные ограничения приложены;
- приложение можно передать для демонстрации только на вымышленных данных.

## 10. Первый рабочий срез

Начинать следует не с нового UI и не с Windows packaging, а с одной вертикальной цепочки:

1. `DemoScenario` contract;
2. accounting + bank scenario connectors;
3. fictional rule bootstrap;
4. `ForecastApplicationFacade`;
5. один base golden test;
6. кнопка запуска в существующем окне.

Этот срез даст первый реально работающий путь «нажал — получил прогноз». После него расширяются представление, сравнение, история и Windows-сборка без изменения базовой оркестрации.
